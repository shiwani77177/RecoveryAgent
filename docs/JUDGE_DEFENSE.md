# Judge Defense

> Anticipated questions and honest answers.

---

## Q: How is this different from just retrying failed payments?

Blind retries waste resources on unrecoverable failures (expired cards, fraud flags)
and miss opportunities for targeted interventions (payment links for card issues,
SMS reminders for insufficient funds). RecoveryAgent diagnoses WHY a payment failed
before deciding WHAT to do, routes each case to the most effective intervention,
and escalates genuinely unrecoverable cases to humans instead of wasting attempts.

The eval harness proves this: the agent consistently outperforms a naive
retry-all baseline across 55 test cases spanning 6 failure categories.

---

## Q: Is the AI actually doing anything useful here?

Yes, but with honest caveats:

**When Gemini is available:** The AI analyzes the error code, amount, and attempt
count to produce a structured diagnosis with root cause, recommended action,
channel, confidence score, and a rationale for the audit trail.

**When Gemini is unavailable** (rate limited, key expired): The system falls back
to a deterministic rule engine (`ruleFallback` in GeminiDiagnosisAgent.java) that
maps error codes to interventions based on domain knowledge. The audit trail
records `(Rule fallback)` prefix so it's transparent.

**The key insight:** The AI adds value not in the action selection (which rules can
approximate) but in the **confidence scoring** and **rationale generation**. Low
confidence triggers automatic escalation to humans. The rationale text in the
audit trail gives operators a clear explanation of why each decision was made.

---

## Q: Is the data real?

No. All 55 test cases are synthetic, generated by `SyntheticDataGenerator.java`.
Every case is labeled `merchant_eval` and has a `trulyRecoverable` ground truth
flag. This is by design — the eval framework needs known ground truth to grade
the agent's decisions.

In production, ground truth would come from actual payment outcomes tracked over
time: did the customer eventually pay? was the charge disputed? This is stated
in `docs/EVAL.md`.

## Q: Why Java instead of Python?

Razorpay's own backend runs on Java/JVM. For a payment infrastructure system
handling real money with ACID requirements, Java + Spring Boot provides:

- Compile-time type safety (catches errors before runtime)
- Mature transaction management (Spring Data JPA + PostgreSQL)
- Production-grade dependency injection (clean architecture)
- Industry standard for fintech backends

Python is faster to prototype but Java signals production-grade engineering judgment.

---

## Q: Why not use a more sophisticated ML model?

We considered training a custom model (XGBoost, logistic regression) on the
synthetic corpus. We chose not to because:

1. **55 training examples is too few** for meaningful ML training
2. **The decision space is small** — 6 intervention types × ~15 error codes
3. **Rules approximate the optimal policy** — insufficient_funds → DUNNING_MESSAGE,
   card_expired → PAYMENT_LINK, fraud → ESCALATE. An ML model would learn
   approximately the same mapping.
4. **Transparency** — a rule fallback is fully interpretable. An ML model is a
   black box that's harder to audit.

The system is designed to swap in a trained model when production data is
available. The `DiagnosisAgent` interface makes this a one-file change.

---

## Q: What happens if the AI goes down?

The system degrades gracefully:

1. **Gemini API returns error** → `GeminiDiagnosisAgent` catches the exception and
   calls `ruleFallback()` — a deterministic switch statement that maps error codes
   to interventions with reasonable confidence scores.

2. **Rule fallback also fails** → `safeEscalate()` returns confidence 0.0, which
   triggers automatic escalation to a human operator.

3. **Redis goes down** → guardrail checks fail, interventions are blocked, cases
   stay in WAITING. No money moves. The system stops rather than guesses.

4. **PostgreSQL goes down** → Spring Boot refuses to start. Docker Compose healthcheck
   ensures the app container waits for Postgres to be ready.

**No failure mode results in uncontrolled money movement.** The system is
fail-closed by design.

## Q: Can the AI override the guardrails?

No. The architecture makes this impossible:

```
DiagnosisAgent.diagnose()    → returns Diagnosis (a data object, no side effects)
GuardrailService.check()     → returns null (safe) or rejection reason (blocked)
InterventionExecutor.execute() → only called if guardrails return null
```

The AI's output is a `Diagnosis` record — a recommendation with no authority.
The `GuardrailService` is a separate class that runs independently. There is no
code path from `DiagnosisAgent` to `InterventionExecutor` that bypasses guardrails.

---

## Q: Why not deploy it live?

Time constraint. The Docker multi-stage build is production-ready and could be
deployed to any cloud provider (AWS ECS, GCP Cloud Run, Railway, Render) with
`docker compose up`. We prioritized a working local demo with real eval numbers
over a deployed instance with potential infra issues during the demo.
